A bug fix for upstream waLBerla, prepared as a patch against its latest release. Not based on our `rvv-support*`
branches: the patch was written and tested in a fresh clone of upstream.

## The bug

waLBerla's buffered communication (`UniformBufferedScheme`, `NonUniformBufferedScheme`) writes a small header
before each block's data in the MPI send buffer: `BlockID::toBuffer` (a length byte and the ID bytes) and the
`stencil::Direction` enum (4 bytes), with `memcpy`. With a one-byte block ID that is 6 bytes, so the data after
it starts 2 bytes off 4-byte alignment. The pack infos of `lbm_generated` then hand that position to generated
kernels, which access it as an array of the field type:

```cpp
// src/lbm_generated/communication/UniformGeneratedPdfPackInfo.h
unsigned char* bufferPtr = buffer.forward(kernels_.size(ci, dir));
kernels_.packDirection(field, ci, bufferPtr, dir);

// python/lbmpy_walberla/templates/LbmStorageSpecification.tmpl.cpp (generated PackKernels::packDirection)
{{dtype}} * buffer = reinterpret_cast<{{dtype}}*>(outBuffer);
```

Accessing a `float`/`double` through a misaligned pointer is undefined behavior in C++. The contract of
`communication::UniformPackInfo` already says so since commit `bd5adb91` ("Fix PackInfo codegen", 2024-11-11),
which fixed the same problem for the pack infos generated by `pystencils_walberla` (`CpuPackInfo.tmpl.h`):

> Implementations must reserve extra space and advance the send buffer pointer according to the alignment of the
> ghost layer data type! The buffer is char-aligned.

Three CPU pack infos were not changed then and still pass unaligned positions:

- `lbm_generated::UniformGeneratedPdfPackInfo` (pack and unpack, "all" and "direction");
- `lbm_generated::NonuniformGeneratedPdfPackInfo` (equal level, coarse to fine, fine to coarse);
- `GeneratedNonUniformFieldPackInfo` (blockforest; equal level, coarse to fine, fine to coarse).

When the data is misaligned depends on the header length. `UniformBufferedScheme` writes `(1 + n) + 4` bytes for an
`n`-byte block ID, so with the common one-byte IDs the data is always 2 bytes off. `NonUniformBufferedScheme` writes
sender and receiver ID and the direction, `2 (1 + n) + 4` bytes: with one-byte IDs that is 8 bytes and `double`
data happens to be aligned, with two-byte IDs (more blocks or refinement levels) it is 10 bytes and misaligned, and
`float` data is misaligned for every even `n`. The payloads that follow each other in one message keep the offset
of the first, since their sizes are multiples of the element size.

Not affected: the pack infos generated by `pystencils_walberla` (fixed in `bd5adb91`), hand-written pack infos that
use `buffer << value` (`memcpy`), and the GPU schemes (`UniformGPUScheme` exchanges the headers in a separate
buffer system, so its data buffers hold the payloads only).

## How it shows

- **x86**: silently, because x86 tolerates misaligned accesses. GCC's or Clang's `-fsanitize=alignment` reports
  it: see [Testing](#testing).
- **RISC-V with the vector extension**: every multi-process run crashes. Found with waLBerla-wind (D3Q27 cumulant,
  `UniformGeneratedPdfPackInfo`) on a Banana Pi BPI-F3 (SpacemiT K1, X60 cores, Linux 6.6.36, GCC 14.2,
  `-O3 -march=rv64gcv_zvl256b`): single-process runs work, every 4-process run dies with
  `Bus error (7), Invalid address alignment`, also without any explicit vector code. GCC auto-vectorizes the
  scalar packing kernel; the loops of the edge directions (3 PDFs per cell) become segment stores
  (`vsseg3e32.v`), the corner loops `vse32.v`, while the face loops (9 PDFs per cell) stay scalar. The X60 raises
  an address-misaligned exception for element-misaligned vector accesses (which the RVV specification allows),
  and Linux emulates misaligned scalar accesses only, so the process gets `SIGBUS`. Under gdb, on all four ranks:
  the buffer positions passed to `packDirection` are `...2`/`...6` (2 bytes off), the fault is
  `vsseg3e32.v v3,(t1)` with `t1 = 0x266ff6`. The standalone reproduction gives the same result: offsets 2 and 6
  fault with `-march=rv64gcv`, offsets 0 and 4 work, and every offset works with `-march=rv64gc`.

## The fix

Two small functions on the buffers, next to `forward()` and `skip()`, which implement the documented contract once
instead of in every pack info, with the same scheme as `bd5adb91`:

```cpp
template< typename V > T * GenericSendBuffer<T,G>::forwardAligned( uint_t elements );
template< typename V > T * GenericRecvBuffer<T>::skipAligned( size_t elements );
```

Both reserve `sizeof(V)` bytes more than requested and return the first position in that range that is aligned
for `V` (`std::align`). Sender and receiver find the same position: both buffers are allocated with `new[]`, which
aligns them for every fundamental type, the data is at the same offset in both, and both advance by the same
number of bytes. The three pack infos call `forwardAligned< value_type >` and `skipAligned< value_type >` instead
of `forward` and `skip`. Cost: up to `sizeof(value_type)` extra bytes per block and direction in a message.

| file | change |
|---|---|
| `src/core/mpi/SendBuffer.h` | `forwardAligned< V >()`, +34 lines with its documentation |
| `src/core/mpi/RecvBuffer.h` | `skipAligned< V >()`, +28 lines with its documentation |
| `src/lbm_generated/communication/UniformGeneratedPdfPackInfo.h` | 4 call sites, 2 comment lines |
| `src/lbm_generated/communication/NonuniformGeneratedPdfPackInfo.impl.h` | 6 call sites |
| `src/blockforest/communication/GeneratedNonUniformFieldPackInfo.impl.h` | 6 call sites |
| `tests/core/mpi/BufferTest.cpp` | `bufferAlignedTest< float/double >`, +39 lines: every header length from 0 to 2·sizeof(V)−1, aligned position, data and the byte after it read back |

In total 119 lines added, 16 changed.

All runs exit with 0, before and after the patch: on x86 the misaligned accesses are silent. The existing tests do
not reach a misaligned case of the two non-uniform pack infos; the patch changes them the same way for the cases
with longer block IDs or `float` data.

Another sanitizer report appears in every run, before and after the patch, and is not addressed here:
`field::aligned_malloc_with_offset` (`src/field/allocation/AlignedMalloc.cpp:85`, and the load in `aligned_free`,
line 98) stores the pointer returned by `malloc` just in front of a block that is aligned with an offset, which can
be a misaligned `void*` store. It is a scalar access, harmless on x86 and on the RISC-V cores we know, but with
`-fno-sanitize-recover=alignment` it aborts the program before any communication happens.

Building and running both took 2 h 26 min on the board (2 parallel jobs). The same crash, with the stack symbolized
to `PackKernels::packDirection` and the faulting instruction `vsseg3e32.v`, is the one found in waLBerla-wind (see

waLBerla-wind's CPU benchmark app on the same board (walberla-rvv-support, `scripts-legacy`, float32, one 64³ block

bus error; with the patch applied to the fork's branch, all 81 timed runs (9 variants × 1, 4 and 8 processes × 3

count to rounding.

## Pull request text

**Title:** Align the data of generated pack infos in communication buffers

**Description:**

The buffered communication schemes write a header (block ID, direction) before each block's data, so the data
starts at an arbitrary byte offset in the buffer. `UniformGeneratedPdfPackInfo`, `NonuniformGeneratedPdfPackInfo`
and `GeneratedNonUniformFieldPackInfo` hand that position to generated kernels that access it as `float*` or
`double*`: undefined behavior, which the contract of `UniformPackInfo` already rules out since bd5adb91, where the
pack infos generated by `pystencils_walberla` were fixed. On x86 it goes unnoticed (`-fsanitize=alignment` reports
it); on RISC-V cores that trap on misaligned vector accesses (SpacemiT X60, GCC with `-march=rv64gcv`), every
multi-process run dies with SIGBUS in the auto-vectorized packing kernel.

This adds `SendBuffer::forwardAligned<V>()` and `RecvBuffer::skipAligned<V>()`, which reserve `sizeof(V)` extra
bytes and return a position aligned for `V` (the scheme of bd5adb91), and uses them in the three pack infos.
`BufferTest` checks the new functions for every header length.

With `-fsanitize=alignment`, `InterpolationNoSlip` on 2 processes (`-DomainSetup.blocks=<2,1,1>`) gives 108
reports of misaligned `double` accesses in the generated packing kernels before this change and none after it. On a
SpacemiT K1 (`-march=rv64gcv_zvl256b`, GCC 14.2) the same run dies with SIGBUS before this change and passes after it.
(`field::aligned_malloc_with_offset` produces another alignment report in every run, unrelated to communication and
not changed here.)
