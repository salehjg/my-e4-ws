\section{Background}

%  The answers, all from the measurements later in the talk (macros). One core: split / plain scalar;
%  vectors alone: the fair test (both machines' output-last rounds); all cores: split / best scalar.
\begin{frame}{What this talk shows}
  \vspace{1mm}
  \begin{itemize}\small
    \item \textbf{The question.} A fluid simulation is generated from Python into C++. Can the generator
          write \term{RISC-V vector} (RVV) code that is correct and fast, on chips with different vector
          widths?
    \item \textbf{What we built.} An RVV target in the code generator (pystencils) and the build system
          (waLBerla). The build measures the chip's vector width and generates code for exactly that width:
          256 bits (SpacemiT K1) or 128 bits (Sophgo SG2044).
    \item \textbf{Correct.} On both machines, all 44 programs (11 builds, 2 compilers, 2 precisions)
          match an independent reference solution to rounding.
    \item \textbf{Faster, one core, f32 (GCC).} The fastest build is \sx{\nv{kone:gcc:f32:1:split/plain}} the
          plain build on the K1 and \sx{\nv{sg:gcc:f32:1:split/plain}} on the SG2044. The vectors alone give
          \sx{\nv{kone:fair:gcc:f32}} of a possible \sx{8} on the K1, and \sx{\nv{sg:fair:gcc:f32}} of a possible
          \sx{4} on the SG2044; the rest comes from computing less and touching fewer arrays.
    \item \textbf{All cores.} With every core busy, memory becomes the limit: the gain over the best
          non-vector build drops to \sx{\nv{kone:gcc:f32:8:split/best}} (K1, 8 cores) and
          \sx{\nv{sg:gcc:f32:64:split/best}} (SG2044, 64 cores).
  \end{itemize}
  \vfill
  {\scriptsize\color{psgray}Order of the talk: what holds on both machines; then the K1; then the SG2044; then
  what can be compared between the two.\par}
\end{frame}

\begin{frame}{RISC-V vectors: each chip chooses its register width}
  \begin{columns}[T,onlytextwidth]
    \column{0.52\textwidth}
    \vspace{4mm}
    \centering\resizebox{0.98\linewidth}{!}{\input{figures/vlen}}
    \column{0.46\textwidth}
    \vspace{2mm}
    \begin{itemize}\footnotesize
      \item \term{RVV}, the RISC-V vector extension, fixes the instructions, not the register width
            \term{VLEN}. Each chip picks its own.
      \item Our two machines: the \term{SpacemiT K1} has VLEN 256, the \term{Sophgo SG2044} has VLEN 128.
      \item Code can be written for any VLEN (it asks the chip at run time), or for one VLEN only. Our generator
            writes code for one VLEN, like the code it writes for x86 (AVX: always 256 bits).
      \item Code for 256 bits run on a 128-bit chip silently computes wrong results. So the width must be
            right: the next part shows how.
    \end{itemize}
  \end{columns}
  \takeaway{One f32 vector instruction: 8 numbers on the K1, 4 on the SG2044. Vectors alone can make the arithmetic
    at most \sx{8} / \sx{4} faster (K1) and \sx{4} / \sx{2} (SG2044), in f32 / f64.}

\begin{frame}{A wrong width gives wrong results, so it is a compile error}
  \vspace{1mm}
  \begin{itemize}\small
    \item \textbf{The danger.} Code for 256 bits asks for 8 f32 numbers per instruction. A 128-bit chip gives 4,
          and the loop still steps by 8: half the cells are never updated. No crash, no warning.
    \item \textbf{Shown in a test.} Six small kernels in a RISC-V emulator (QEMU) set to 128 bits: the 256-bit
          code gets 30 to 55 of 115 cells wrong per kernel. The 128-bit code is right at 128 and at 256 bits.
    \item \textbf{Caught at compile time.} The generated file includes a header that stops the compiler
          (\code{\#error}) unless the flags promise at least the width the code was made for. 256-bit code with
          128-bit flags does not compile.
    \item \textbf{What it cannot catch.} The flags are a promise about the chip, not a measurement. That is why
          the build measures the width on the machine itself.
  \end{itemize}
  \vfill
  {\scriptsize\color{psgray}Laptop tests: 154 RVV tests in pystencils pass, among them the emulator runs at 128
  and 256 bits.\par}
  \takeaway{A mismatch between code and flags stops the build. The flags come from the chip.}
\end{frame}

\section{How the kernel works}

\begin{frame}{The stencil: the cells needed to update one cell}
  \begin{columns}[T,onlytextwidth]
    \column{0.53\textwidth}
    \vspace{4mm}
    \centering\input{figures/stencil-d3q19}
    \column{0.45\textwidth}
    \vspace{1mm}
    \begin{itemize}\small
      \item Each cell stores 19 values, $f_0$ to $f_{18}$. Each value is the fluid moving in one of
            19 directions (\term{D3Q19}).
      \item<2-> In every time step, each value moves one cell along its direction. The kernel
            \term{pulls}: each cell fetches $f_i$ from the neighbour it comes from. $f_4$ moves east, so
            it comes from the west neighbour.
      \item<4-> The \term{stencil} is the set of cells needed to update one cell: the cell itself, 6 face
            neighbours and 12 edge neighbours. The 8 corners are not used.
    \end{itemize}
  \end{columns}
  \vfill
  {\scriptsize\color{psgray}The numbering follows lbmpy. LBM papers call this move ``streaming''; it is unrelated
  to the data streams later in the talk.\par}
  \takeaway{To update one cell, the kernel reads 19 values: from the cell itself and from 18 neighbours.}
\end{frame}

% -----------------------------------------------------------------------------
\begin{frame}{How the 19 values are stored in memory}
  \centering\input{figures/field-layout}

  \raggedright
  \uncover<6->{\footnotesize Each of the 19 values ($f_0$ to $f_{18}$) has its own 3D array like this, and the 19
  arrays follow each other (\term{layout fzyx}).\par
  {\scriptsize\color{psgray}Our blocks have $64^3$ cells. The \term{ghost layer} wraps the whole block (66 cells in
  $x$, $y$ and $z$) and holds the values of the neighbouring block or of the wall. The \term{padding} makes every
  row start at a multiple of 16 bytes (the same on both machines).\par}}
  \takeaway{Neighbours in $x$ are next to each other; the 19 values of one cell are 1.2\,MB apart (f32).}
\end{frame}

\begin{frame}{The kernel code: updating one cell, step by step}
  \vspace{-1mm}
  \centering\input{figures/kernel-code}

  version, which updates L cells per iteration: L = 4 on the SG2044, 8 on the K1 (f32).\par}

\end{frame}

% -----------------------------------------------------------------------------
\begin{frame}{What a data stream is, and why our loop has 42}
  \begin{columns}[T,onlytextwidth]
    \column{0.55\textwidth}
    \vspace{1mm}
    \centering\input{figures/stream-def}
    \column{0.43\textwidth}
    \vspace{1mm}
    \begin{itemize}\small
      \item \term{Stream}: the loop reads or writes one array at consecutive addresses, cache line
            after cache line. The \term{hardware prefetcher} spots this and loads the next lines early.
      \item<4-> Each of the 19 values of a cell has its own array. One step of the loop reads 19 arrays,
            writes 19 others and 4 outputs ($\rho$, $u$): 42 streams.
    \end{itemize}
  \end{columns}
  \vfill
  {\scriptsize\color{psgray}The term in lattice Boltzmann performance papers: ``concurrent memory streams
  (38 with OS-NT and 19 with AA)'' for D3Q19 (Wittmann et al., arXiv:1410.0412).\par}
  \takeaway{A stream is one sequence of addresses the loop walks through. Our loop walks through 42 at once.}
\end{frame}

% -----------------------------------------------------------------------------
\begin{frame}{How many streams the stencil needs}
  \begin{columns}[T,onlytextwidth]
    \column{0.6\textwidth}
    \vspace{1mm}
    \input{figures/stream-count}
    \column{0.38\textwidth}
    \vspace{1mm}
    \begin{itemize}\footnotesize
      \item Drawn in one array, as on the memory slide: 12, 13 and 14 share a row and a cache line, so the loop
            reads them in one stream. 10 and 16 lie in other rows, 4 and 22 in other planes: 5 streams.
      \item<2-> In our kernel each value has its own array: $f_4$ comes from cell 12 of array $f_4$, $f_1$ from
            cell 10 of array $f_1$, and so on. Each array is read at one place only, so every read is a stream
            of its own.
      \item<3-> The loop also writes the 19 new values and 4 outputs ($\rho$, $u$) into arrays of their own:
            $19 + 19 + 4 = 42$ streams. In place (AA), the reads and writes use the same 19 arrays: 23.
    \end{itemize}
  \end{columns}
  \vfill
  \takeaway{Each array the loop reads or writes is one stream: $19 + 19 + 4 = 42$.}
\end{frame}

\begin{frame}{Summary, and what is still open}
  \vspace{1mm}
  \begin{itemize}\small
    \item \textbf{One generator, two widths.} pystencils and waLBerla generate RVV code for 128 or 256 bits; the
          build measures the width. A mismatch is a compile error. The K1's code did not change.
    \item \textbf{Correct on both.} 44 of 44 programs per machine match the reference solution to rounding.
    \item \textbf{Faster on both.} One core, f32, GCC: \sx{\nv{kone:gcc:f32:1:split/plain}} (K1) and
          \sx{\nv{sg:gcc:f32:1:split/plain}} (SG2044) over plain scalar. The vectors alone give about \sx{2} of it
          (fair test); the rest comes from CSE and fewer data streams (in place, split loop).
    \item \textbf{All cores.} Memory becomes the limit: \sx{\nv{kone:gcc:f32:8:split/best}} (K1, 8 cores) and
          \sx{\nv{sg:gcc:f32:64:split/best}} (SG2044, 64 cores) over the best scalar build.
  \end{itemize}
  \vspace{1mm}
  {\small\bfseries Open\par}
  \begin{itemize}\small
    \item Clang's in-place + prefetch kernel without density/velocity output runs at half speed on the SG2044. Why?
    \item Tuning per chip: register grouping (LMUL), prefetch distance, split block sizes. The generator has the
          options; no sweep was run yet.
    \item Does the SG2044's core run the prefetch hint? A stream test like the K1's would tell.
    \item Memory layout effects (huge pages) were only tested on the K1.
  \end{itemize}
\end{frame}

\begin{frame}{Glossary (1/3)}
  \begin{columns}[T,onlytextwidth]
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[AA pattern] in-place update: one array (A) is read and written; even and odd steps alternate.
      \item[AB pattern] the usual update: read array A, write array B, then swap.
      \item[Auto-vectorization] the compiler turns a plain loop into vector code by itself.
      \item[Best scalar build] no vector instructions, but with the other improvements (CSE, AA pattern).
      \item[Block] a box of cells; waLBerla cuts the domain into blocks, here one per process.
      \item[Bounce-back] wall rule: a value that would flow into the wall comes back in the opposite direction.
      \item[C920v2] the XuanTie core type of the SG2044.
      \item[Cache line] the unit the memory system moves: 64 bytes.
      \item[Cache miss] the data is not in the cache and must come from main memory.
      \item[CSE] common sub-expression elimination: compute each repeated part of a formula once.
    \end{description}
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[D3Q19] the LBM model used: 3 dimensions, 19 directions per cell.
      \item[f32, f64] single (32-bit) and double (64-bit) precision floating point.
      \item[GCC, Clang] the two C++ compilers we compare.
      \item[Ghost layer] a one-cell copy of the neighbour block's border around each block.
      \item[Halo exchange] refreshing the ghost layers after each time step.
      \item[Hardware prefetcher] part of the cache that spots regular access patterns and loads data early.
      \item[Hint] an instruction that cores without the extension run as a no-op.
      \item[Huge page] a 2\,MB page of memory instead of 4\,KB: fewer address translations.
      \item[In order] a core that runs instructions strictly in program order: it waits for each missing value.
      \item[Interleaved rounds] every build runs once per round, so slow drifts hit all builds alike.
    \end{description}
  \end{columns}
\end{frame}

\begin{frame}{Glossary (2/3)}
  \begin{columns}[T,onlytextwidth]
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[Intrinsic] a C/C++ function that the compiler turns into one machine instruction.
      \item[K1, X60] the SpacemiT chip on the board, and its core type.
      \item[Kernel] the generated loop that updates all cells once.
      \item[Lane] one number's slot in a vector register.
      \item[Layout fzyx] waLBerla's memory order: $x$ fastest, then $y$, then $z$; each value $f_i$ has its own array.
      \item[LBM] lattice Boltzmann method: fluid simulation on a grid of cells.
      \item[lbmpy] Python package that derives the LBM formulas for one cell.
      \item[Lid-driven cavity] a closed box whose top wall moves: a standard flow test case.
      \item[MLUP/s] million cell updates per second.
      \item[Monte Cimone] a RISC-V cluster; one of its nodes has the SG2044.
    \end{description}
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[MPI] the standard library for messages between processes; Open MPI is one implementation.
      \item[Periodic box] the earlier test case: no walls, what leaves one side comes back on the other.
      \item[Plain scalar build] the same program compiled without any vector instructions.
      \item[Pull] each cell fetches every value from the neighbour it comes from.
      \item[pystencils] Python package that turns formulas into a C++ loop over all cells.
      \item[RISC-V] an open instruction set architecture.
      \item[RVV] the RISC-V vector extension.
      \item[SG2044] the Sophgo chip with 64 cores used in part 2.
      \item[sha256] a checksum of a file: the same file always gives the same value.
      \item[slurm] the queue that hands out cluster nodes to jobs.
    \end{description}
  \end{columns}
\end{frame}

\begin{frame}{Glossary (3/3)}
  \begin{columns}[T,onlytextwidth]
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[Software prefetch] an instruction that asks the cache to load data that will be needed soon.
      \item[Split loop] the cell update in 8 short passes over a block of 1 or 2 rows, few arrays per pass.
      \item[Stall] a cycle in which the core cannot go on: it waits for data or for a result.
      \item[Stencil] the set of cells needed to update one cell; here 19 (D3Q19).
      \item[Stream] one run of consecutive addresses that a loop walks through, e.g.\ one array.
      \item[Stride] the address distance between two neighbouring cells of a loop.
      \item[sweepgen] part of waLBerla: wraps generated kernels into C++ classes.
    \end{description}
    \column{0.49\textwidth}
    \scriptsize
    \begin{description}\setlength{\itemsep}{0.8pt}
      \item[vl] vector length: how many numbers one RVV instruction works on.
      \item[VLEN] the width of a chip's vector registers in bits: 256 (K1), 128 (SG2044).
      \item[waLBerla] open-source C++ framework for fluid simulations.
      \item[Wall pass] the sweep that applies bounce-back to the cells next to a wall.
      \item[Weak scaling] more cores, larger domain, the same work per core.
      \item[Write-allocate] before a store, the cache first loads the line from memory.
      \item[Zicbop] the RISC-V extension with prefetch instructions.
    \end{description}
  \end{columns}
\end{frame}

\begin{frame}{SG2044: the MPI problem, and the fix}
  \vspace{1mm}
  \centering
  {\footnotesize\renewcommand{\arraystretch}{1.15}
  \begin{tabular}{@{}lll@{}}
    \toprule
    & \textbf{system Open MPI 4.1.5} & \textbf{Open MPI 5.0.6 (module)}\\
    \midrule
    helper thread per process & busy (100\,\%), shares the rank's core & idle (0\,\%)\\
    exchange of 1\,KiB / 64\,KiB, 4 processes & 10\,000\,$\mu$s / 30\,000\,$\mu$s & 9.6\,$\mu$s / 209\,$\mu$s\\
    hangs & 16-process run; all-to-all test & none (2 to 64 processes)\\
    \bottomrule
  \end{tabular}\par}
  \vspace{3mm}
  \raggedright
  \begin{itemize}\small
    \item With one core per process, the busy helper thread took half of each core, and every message waited for
          the scheduler's 10\,ms turn. Timings made with it were thrown away; the build was repeated with 5.0.6.
    \item The timing job checks MPI before each process count. Halo-like exchange, 64\,KiB to each neighbour:
          \nv{sg:mpihalo:4}\,$\mu$s (4 processes) to \nv{sg:mpihalo:64}\,$\mu$s (64 processes) per exchange, every
          byte right, helper thread at 0\,\%.
  \end{itemize}
  \takeaway{All SG2044 numbers in this talk come from one session with Open MPI 5.0.6.}
\end{frame}

\begin{frame}{How the results are checked, in detail}
  \vspace{1mm}
  \begin{itemize}\small
    \item \textbf{Reference cases}: 1 process $16^3$ at 100 and 101 steps (even and odd: the in-place builds
          alternate), 2 processes $32\times16\times16$, 6 processes $16\times24\times8$. Per build: largest
          difference of density and velocity, mass, mirror symmetry.
    \item \textbf{Decomposition}: $32^3$ on 1 process against 8 processes of $16^3$: bit for bit.
    \item \textbf{Compilers}: GCC against Clang on every reference case.
    \item \textbf{Builds}: every compile line checked for its \code{-march} and \code{-O3}; scalar programs contain 0
          vector instructions; RVV kernels contain them; on the SG2044 every program links Open MPI 5.0.6.
    \item \textbf{Timed runs}: the programs' sha256 must be in the verification log; every run of a build ends in
          the same field hash; the 11 builds agree in energy (table on the checks slide).
  \end{itemize}
  \vfill
  {\scriptsize\color{psgray}Checks re-done for these slides by \code{scripts/presentation7/slide\_data.py}, which stops
  if any fails: run counts, steps, block counts, compilers, field hashes, energies, VERIFY PASS, BUILD PASS, TIME
  DONE, and the job's own best-of table (all 176 SG2044 values equal). Not checked: box sizes that are not a
  multiple of the vector length.\par}
\end{frame}
