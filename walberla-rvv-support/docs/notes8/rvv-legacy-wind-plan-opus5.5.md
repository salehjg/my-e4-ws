## 1. Context

waLBerla-wind (`submodules/waLBerla-wind`, the lattice Boltzmann solver for wind turbines and wind farms of Schottenhamml
et al.) is the application we want to run with RVV. A waLBerla developer told the user that waLBerla has two cores, a
legacy one and a new one, that waLBerla-wind uses the legacy one, and that the legacy core already supports the AA
streaming pattern. Reading the code confirms all three statements.

All our RVV work so far is on the new core:

- pystencils fork, branch `rvv-support`, on upstream master `20d7dcf0` (2026-05-21, `release/2.0b1` plus 2 commits):
  the RVV backend `RvvCpu`/`SelectIntrinsicsRvv` (`backend/platforms/rvv.py`), the targets `RISCV_RVV128`/`RISCV_RVV256`,
  software prefetch, `.vf` operands and FMA, row pointers, LMUL.
- walberla fork, branch `rvv-support`, on upstream master `0c8ed8c9` (2026-05-21): RISC-V CMake (VLEN, `-march`,
  `-mtune`), AA in sweepgen and in the v8 halo exchange, the apps `SweepgenLbmCPU` and `SweepgenLdcCPU`.

waLBerla-wind can use none of the Python code: its kernels are generated by the legacy code generator, which needs
pystencils 1.x. So a lot of the work has to be redone on pystencils 1.4.

Goals, decided with the user (2026-11-26):

1. **G1, waLBerla-wind on RISC-V.** waLBerla-wind builds, verifies and runs on the K1 (bananapi) and the SG2044
   (monte3) against our walberla fork.
2. **G2, where we stand.** pystencils 1.4 already has an RVV instruction set (upstream `rvv`). We clone it into our own
   instruction set, leave upstream `rvv` untouched next to it, and build our features on the clone. Then we benchmark
   upstream `rvv`, our clone with each feature, and our 2.x backend (sweepgen) against each other.
3. **G3, AA in waLBerla-wind** through the legacy core's in-place streaming.

Rules for all of this work, set by the user (2026-11-26):

1. **Simple first.** If something can be implemented simply, implement it that way, not with a lot of clever code
   that is hard for humans to maintain. Whatever we reuse from our own earlier code (the pystencils 2.x backend, our
   walberla additions) is first simplified where possible and then migrated.
2. **Upstream code stays as its developers wrote it.** Only our own additions are ours to shape. In files of
   pystencils, waLBerla and waLBerla-wind we add the minimum (a dispatch line, an include, a hook) and follow the
   file's style; new logic goes into new files of our own.

The kernel (all paths in `submodules/waLBerla-wind`):

- D3Q27 cumulant (Galilean correction, fourth-order correction 0.1), Guo forcing, QR subgrid model, compressible,
  zero-centered, layout fzyx. float32 in CI (`WALBERLA_DOUBLE_ACCURACY=OFF`).
- Streaming: `'pull'` is hard-coded in the apps (`apps/GeneratedApp_cpu_uniform/LBMGeneration.py`), and the README
  says only pull is supported (`README.md:72`). But the AppGenerator offers all six patterns
  (`apps/AppGenerator/jinja_filters/enums.py`), already has in-place branches (`MacroGetter_EVEN/_ODD`), and the GPU
  benchmark app uses aa (`apps/BenchmarkApp_gpu_staticRefinement/LBMGeneration.py:103`).
- AA blockers on the CPU:
  - Shifted-periodic inflow refuses in-place patterns (`apps/AppGenerator/templates/main.tmpl.cpp:136`).
  - `StrainRateWriter` reads `pdfs.center_vector` directly (`apps/AppGenerator/templates/GenerationScript.tmpl.py:316-322`).
    Under AA the stored values after an even step are post-collision and sit in the opposite direction's slot, so the
    strain rate comes out wrong.
- Vectorization: `cpu_vectorise_info = {'nontemporal': True}` (`GenerationScript.tmpl.py:340`). The instruction set
  comes from `get_vectorize_instruction_set` (`submodules/walberla/python/pystencils_walberla/utility.py:70-88`): `None`
  unless `WALBERLA_OPTIMIZE_FOR_LOCALHOST` is on, then the host's best set, or `'sse'` if detection finds nothing (`:86`).
  On RISC-V that fallback would put x86 intrinsics into the code.
- The turbine models (actuator line/disk, DISCON controllers) are hand-written C++; no x86 intrinsics or `-march`
  flags anywhere in waLBerla-wind.

### 1.3 pystencils 1.4 and its RVV instruction set

- Tag `release/1.4` (`48474c1a`, 2025-10-17), the last 1.x release. It sits on the same master line as our 2.x branch
  (an ancestor of `rvv-support`); the 2.0 rewrite was merged after it (`v2.0-prerelease`, 2026-05-04; `release/2.0b1`,
  2026-05-07).
- Design: sympy assignments → AST (`pystencils.astnodes`) → transformations (constants before the loop, one base pointer
  per field access row, OpenMP, blocking) → `vectorize()` (`cpu/vectorization.py:76`) → C code printed by
  `backends/cbackend.py`. Each instruction set is a dictionary of C string templates
  (`backends/{x86,arm,ppc,riscv}_instruction_sets.py`), filled in by one printer for all of them
  (`VectorizedCustomSympyPrinter`). The dispatcher is `get_vector_instruction_set` (`backends/simd_instruction_sets.py:29-30`
  for rvv); detection reads AT_HWCAP bit V (`:71-75`); `PYSTENCILS_SIMD` overrides it.
- RVV (`backends/riscv_instruction_sets.py`, Michael Kuron; ratified `__riscv_` intrinsic names since `b4d7ef7c`,
  2025-07-04):
  - vector-length agnostic: the loop step is `__riscv_vsetvlmax_e<SEW>m1()` at run time (`:84`), LMUL 1;
  - every intrinsic gets `vl = loop_stop - loop_counter` (`:65`), so there is no scalar tail loop;
  - strided and masked loads/stores;
  - for nontemporal stores, `cbo.zero` (Zicboz) before writing a cache line, only when the compiler defines
    `__riscv_zicboz` (`:109`, `include/riscv_v_helpers.h`, printer `cbackend.py:315-326`);
  - no FMA, no `.vf` operands, no prefetch, no fixed VLEN, no min/max templates.

## 2. What carries over from the `rvv-support` branches

Commits: pystencils `31758e93` (first VLA+VLS attempt, replaced), `9a989e16` (VLS backend, VLEN 256), `026baf7f`
(prefetch), `a81dc547` (`.vf`, FMA, row pointers, `in_register`), `cf11c388` (VLEN 128/256, LMUL), `78afe1ff` (Clang
17 fix); walberla `e9712d59` to `42855054`.

pystencils 2.x has a typed intermediate representation, platform classes and an intrinsic selection pass; our backend
is pattern matching on that representation. pystencils 1.4 prints string templates. So none of our pystencils Python
code can be copied: the ideas, the C++ helpers and the test approach carry over.

Gains below were measured with the 2.x backend on the K1, D3Q19 SRT
([`../notes3/rvv-8x-speedup-progress-fable5.2.md`](../notes3/rvv-8x-speedup-progress-fable5.2.md)).

| what we built | on the legacy core / pystencils 1.4 | work | measured gain |
|---|---|---|---|
| CMake: `RiscvVlen.cmake`, riscv `-march=rv64gcv_zvl<V>b` and `-mtune` in `GNU.cmake`/`Clang.cmake` | applies to legacy builds as is; already on the walberla branch | none | — |
| RVV code generation | upstream 1.4 `rvv` (§1.3); correct on VLEN 128 and 256 | none | baseline of G2 |

| output-free sweeps | not needed: waLBerla-wind needs ρ and u every step (turbines) | — | — |

Simpler on 1.4 than on 2.x (rule 1), from reading both code bases:

- **`.vf` operands.** In 2.x hoisted constants are vector symbols, so `SelectIntrinsicsRvv` tracks which symbols are
  uniform, declares scalar twins and checks for reassignments (about 100 lines: `_is_uniform`, `_uniform_scalar`,
  `_reassigned`). In 1.4 hoisted constants stay scalar declarations, and the printer sees a scalar symbol or number
  inside a vector expression (it wraps it in `makeVecConst`). Choosing the `.vf` form is then a local decision at
  print time, without any bookkeeping.
- **FMA.** 2.x recognizes products in already lowered intrinsic calls by their names. In 1.4 the printer gets the
  sympy `Add` with its `Mul` terms, so `a*b + c` is visible directly.
- **Row pointers.** 1.4 already hoists one base pointer per field and (y, z, f) offset. Only the x offsets remain;
  whether that matters is measured before anything is written.
- **Prefetch.** One small pass over the innermost vectorized loop (one prefetch per distinct base pointer and
  offset), without the 2.x platform hooks.

### 3.2 Our instruction set `rvv_ext` (pystencils 1.4)

- A copy of `backends/riscv_instruction_sets.py` as `backends/riscv_ext_instruction_sets.py`, registered as
  `rvv_ext` in `get_vector_instruction_set` (the name is open). Upstream `rvv` and its files stay byte-identical.
- Every feature is a knob: a new key of `cpu_vectorize_info`, which `create_kernel` passes on to
  `vectorize(**cpu_vectorize_info)` (`kernelcreation.py:155`). `vectorize()` gets new keyword arguments, all off by
  default and refused for other instruction sets.

| knob | values | does | 2.x origin |
|---|---|---|---|
| `rvv_vlen` | `None`, 128, 256 | `None`: vector-length agnostic like upstream. 128/256: fixed width (literal step and `vl`, scalar remainder loop, compile-time VLEN guard) | `RISCV_RVV128`/`256` |
| `prefetch_distance` | `None` or bytes | `prefetch.r`/`prefetch.w` per distinct access, that many bytes ahead | `InsertPrefetches` |
| `vf_operands` | bool | an operand equal in all lanes is passed as a scalar (`vfadd_vf`, `vfrsub_vf`, ...) | `SelectIntrinsicsRvv` |
| `fma` | bool | `a*b + c` → `vfmacc`, `a*b - c` → `vfmsac`, `c - a*b` → `vfnmsac` | `SelectIntrinsicsRvv` |
| `row_pointers` | bool | one base pointer per access including its x offset; constants through `in_register` | `HoistRowPointers` |
| `rvv_lmul` | 1, 2, 4 | register groups | `cpu.vectorize.rvv_lmul` |

- With every knob off, `rvv_ext` prints exactly upstream's `rvv` code (a golden test, §6), so every gain is measured
  against upstream, one knob at a time.
- The logic lives in our own module next to the copied instruction set. The upstream files
  (`backends/simd_instruction_sets.py`, `backends/cbackend.py`, `cpu/vectorization.py`) only get hook lines, which
  act on template keys that only `rvv_ext` has (rule 2). The output for x86, ARM and upstream `rvv` must stay
  byte-identical (golden test).
- Runtime helpers (prefetch, `in_register`, VLEN guard) go into a new `include/riscv_v_ext_helpers.h`;
  `riscv_v_helpers.h` stays unchanged.
- Order of work follows the measured value: prefetch, `.vf`, FMA, VLS, row pointers, LMUL. The cumulant kernel does
  far more arithmetic per cell than D3Q19 SRT and has 54 PDF streams in pull, so the ranking may differ there; the
  measurements decide.

### 3.6 How the RVV code is developed and tested

The laptop is x86, so the RVV code is developed and checked in three levels, as for the 2.x backend in notes7:

1. **Code generation, plain Python on the laptop.** pystencils writes RVV C code on any host: the instruction set is
   only a string (`instruction_set='rvv'` or `'rvv_ext'`, or `PYSTENCILS_SIMD=rvv,rvv_ext`). We read the generated
   intrinsics and run golden-output tests (§6). This is the fast inner loop.
2. **Running the code under QEMU on the laptop.** The cross compiler `riscv64-linux-gnu-g++` (GCC 16.2) and
   `qemu-riscv64` (11.1) are installed.
   - Our notes7 way: a generated kernel plus a small C driver, cross-compiled with
     `-march=rv64gcv_zvl128b` or `zvl256b` and `-static`, run with `qemu-riscv64 -cpu rv64,v=true,vlen=128|256` (also
     512, to check the vector-length-agnostic mode), results compared with NumPy.
   - pystencils 1.4's own way: its CI runs the whole test suite in an emulated riscv64 container with
     `PYSTENCILS_SIMD=rvv`, `QEMU_CPU=rv64,v=true,zicboz=true` and clang `-march=rv64imfdvzicboz`
     (`.gitlab-ci.yml:202-213` at `release/1.4`). Locally this needs a container runtime and QEMU registered for
     riscv64 binaries (not set up yet); then 1.4's vectorization tests run on `rvv` and `rvv_ext` as they are.
3. **The K1.** The same pytest natively (a 1.4 version of `test.on.bananapi.sh`), and every timing. QEMU checks
   correctness only.

waLBerla kernels (`UniformGridCPU`, waLBerla-wind's cumulant kernel) are generated on the laptop and checked one
kernel at a time under QEMU; whole applications are built and run on the K1. Cross-building waLBerla and MPI for QEMU
is possible but slow, so only if a bug cannot be reproduced at kernel level.

## 4. Implementation steps

Step 1 (waLBerla-wind against our waLBerla, on x86) and steps 2 to 4 (the RVV code in pystencils, §3.6) do not
depend on each other and run in parallel. Step 1 only checks that our waLBerla fork does not break waLBerla-wind; it
uses no RISC-V and no vectors on purpose.

**Step 0, branches and environment.** The branches exist (§3.1). The laptop venv (§3.3).

**Step 1, laptop (x86), baseline.** waLBerla-wind (`GeneratedApp_cpu_uniform`, `LBM_CPU`) against our walberla
`rvv-support-legacy`, pull, float32, `WALBERLA_OPTIMIZE_FOR_LOCALHOST=OFF` as in CI; then
`ctest -L walberlawind::nonRegressionTests`. This shows that the 32 upstream commits and our RISC-V CMake after the CI
pin do not break waLBerla-wind.

**Step 2, laptop, upstream `rvv`.** Generate the `UniformGridCPU` kernels (D3Q19 SRT; D3Q27 cumulant-K17, which is the
`Method.CUMULANT` waLBerla-wind uses, and qr; pull and aa) and waLBerla-wind's kernels with `instruction_set='rvv'`
(`PYSTENCILS_SIMD=rvv` on x86). First question: does 1.4 vectorize the cumulant + QR kernel at all? Then cross-compile
(`riscv64-linux-gnu-g++ -march=rv64gcv_zvl128b` and `zvl256b`) and check single kernels under QEMU against their
scalar versions.

**Step 3, the clone.** `rvv_ext` as an exact copy; golden tests (§6).

**Step 4, the knobs**, one at a time in the order of §3.2, each with code generation tests and QEMU tests.

**Step 5, walberla plumbing** (§3.4) and the `UniformGridCPU` variants; generation checked on the laptop, RISC-V
builds on the K1.

**Step 6, waLBerla-wind** (§3.5): AA, the benchmark app, the variants. On the laptop (x86): AA and pull agree to
round-off after N steps.

**Step 7, K1.** With `scripts-legacy/` (added after the plan, on the user's request; `scripts-legacy/README.md`):
`remote.py push` (the whole git repository to `my-e4-ws-legacy`), then `remote.py start all wind` and
`start all ugc`: build, check (quick run, checksums) and time in `screen`; results in `results-legacy/`.

**Step 8, monte3**, only after asking the user: a monte3 entry in `scripts-legacy/` (sbatch), following notes7's
`monte3.sh`, with the milkv `openmpi-5.0.6` module.

**Step 9, progress log** `rvv-legacy-wind-progress-opus5.5.md` and a notes8 section in the README.

## 5. Measurements

- **(a) Legacy `UniformGridCPU`, lid-driven cavity, 64³ cells per process:** D3Q19 SRT and D3Q27 cumulant-K17 (and
  qr) × pull / aa × {scalar, autovec, `rvv`, `rvv_ext` with each knob} × f32 / f64; K1 at 1, 4, 8 processes, SG2044 at
  1 to 64.

## 6. Verification

1. **Golden output (laptop):** the generated C code for x86 (sse, avx, avx512), ARM (neon, sve) and upstream `rvv` is
   unchanged by our pystencils changes; `rvv_ext` with every knob off prints the same code as `rvv`.
2. **QEMU (laptop):** kernels (elementwise with odd sizes, a stencil, a D3Q19 and a D3Q27 collision) for `rvv` and
   `rvv_ext` (each knob) are cross-compiled with `-static`, run under `qemu-riscv64 -cpu rv64,v=true,vlen=128|256` and
   compared with NumPy, the concept of `tests/nbackend/test_rvv_qemu.py` on the 2.x branch. Fixed-width code for VLEN
   256 must not compile with `zvl128b` (guard).
3. **waLBerla:** `UniformGridCPU` cavity fields against `scripts/notes7/ldc_reference.py`; aa against pull; one block
   against several blocks bit-identical.
4. **waLBerla-wind:** the non-regression tests (float32, absolute tolerance 1e-6 on references made on x86 without
   FMA: FMA may need a documented tolerance), and aa against pull after N steps.

## 7. Risks and open questions

- pystencils 1.4's vectorizer may refuse the cumulant + QR kernel (no min/max templates for RVV); then that support is
  the first piece of `rvv_ext`.
- RVV leaves `vl` open when the requested length is between VLMAX and 2·VLMAX (the hardware may then pick less than
  VLMAX). Upstream's `vl = loop_stop - loop_counter` steps by VLMAX, so on such hardware it would skip elements; QEMU
  and the two boards likely always pick VLMAX. The tests should cover it, and fixed-width mode avoids it.
- Python 3.12 on the K1 (not checked yet); sympy 1.12.1 next to the 2.x venv.
- Ask the waLBerla developer whether `lbmpy_walberla`/`lbm_generated` will move to pystencils 2. If so, our 2.x
  backend would become usable directly and part of this rework unnecessary.
