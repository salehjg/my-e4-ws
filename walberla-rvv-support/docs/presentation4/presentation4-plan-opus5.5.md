### Is it possible? What I found, with evidence

- waLBerla has LDC setups in 4 places:
  - `apps/benchmarks/UniformGridCPU`: `simulation_setup/benchmark_configs.py:37` `ldc_setup`, with the N face
    a UBB lid at u=(0.05,0,0) (`UniformGridCPU.py:156`), the other 5 faces NoSlip, and omega 1.8 (Scenario default).
  - `apps/benchmarks/NonUniformGridCPU/LdcSetup.h`, with grid refinement.
  - `tests/lbm_generated/LDC.cpp`.
  - `apps/tutorials/lbm/03_LBLidDrivenCavity.cpp`.
- **None of them can use our RVV code.**
  - UniformGridCPU and NonUniformGridCPU are generated by `python/pystencils_walberla` and `lbmpy_walberla`.
    Those import pystencils 1.x modules (`pystencils.astnodes`, `pystencils.backends.cbackend`,
    `pystencils.typing.typed_sympy`). None of these exist in our pystencils 2.0 fork (checked in `src/pystencils/`).
  - LDC.cpp uses the pre-generated scalar `src/lbm_generated` kernels.
  - The tutorial uses hand-written `lbm::` kernels.
  - The RVV backend reaches waLBerla only through sweepgen (v8).
- **It is possible as a new sweepgen app.** It reuses presentation3's exact `LbmBulk` kernels and adds walls
  through `sweepgen.boundaries.SparseBoundary` with lbmpy's `NoSlip` and `UBB`. This is the pattern of
  `apps/examples/FlowAroundSphere/FlowAroundSphereExample.{py,cpp}`: `XFactory{...}.fromLinks(pred)`, and the
  boundary sweeps run after stream-collide and the halo exchange.
- Blocker for in-place AA: `sweepgen/src/sweepgen/boundaries/sparse.py` (`_get_kernel_assignments`)
  hardcodes `streaming_pattern = "pull"`. lbmpy itself supports AA boundaries:
  `BetweenTimestepsIndexing(prev_timestep=EVEN|ODD, streaming_pattern="aa")` in
  `lbmpy/advanced_streaming/indexing.py`. Plan: an **app-local** subclass. sweepgen does not change.
- Clang 18.1.8 has never built the current AA/prefetch/split targets. The Clang build dirs on the board
  predate them: `walberla-build-clang-*` has no `SweepgenLbmCPU_explicit_cse_aa_pf` flags.make.
- "Really scalar": presentation3's `SweepgenLbmCPU_scalar_cse_aa` contains **5,795 RVV instructions**.
  All of them sit in waLBerla library code (BlockForest setup, MPI I/O, logging), because only the app's own
  files get `-march=rv64gc`; the libraries are built with `-march=rv64gcv_zvl256b`. The system libraries
  (libc, libstdc++, libm, libmpi, libopen-pal) contain 0. GCC's default is `-march=rv64imafdc_zicsr_zifencei`,
  and Clang's default has no V. GCC 14.2 rejects `-mtune=spacemit-x60` (empty
  `WALBERLA_CXX_SUPPORTS_RISCV_HOST_TUNE`); Clang accepts it (Clang.cmake:37-45).

### Decisions (user, 2026-11-17)

- All 11 presentation3 variants, AA and split included.
- 1, 4 and 8 cores, with one 64³ block per core.
- Compressible D3Q19 SRT, the same bulk kernel as presentation3. Lid u=(0.05,0,0), omega=1.8 (UniformGridCPU's LDC values).
- Compiler flags: waLBerla's defaults. Everything must be -O3. Scalar baselines must be truly scalar, with no autovectorization anywhere.

## Stage 1: the app, built and verified on local x86 first

New directory `submodules/walberla/apps/benchmarks/SweepgenLdcCPU/`. The only edit to an existing fork file is
one line in `apps/benchmarks/CMakeLists.txt`: `add_subdirectory( SweepgenLdcCPU )` inside the existing
`WALBERLA_ENABLE_SWEEPGEN` guard.

- **`CMakeLists.txt`**: a copy of SweepgenLbmCPU's `sweepgen_lbm_variant` logic with the same 11 targets
  (`SweepgenLdcCPU_{scalar,scalar_cse,scalar_cse_aa,autovec,autovec_cse,autovec_cse_aa,explicit_cse,
  explicit_cse_pf,explicit_cse_aa,explicit_cse_aa_pf,explicit_cse_aa_split}`, exactly the 11 that
  `scripts/presentation3/{scalar,autovec,rvv}.sh` run). It keeps the per-target `-march=rv64gc` for scalar and the split sizes
  `2,5,3` (f32) and `1,5,3` (f64).
- **`SweepgenLdcCPU.py`**: the same `LbmBulk` arguments as `SweepgenLbmCPU.py` (D3Q19, SRT, compressible,
  `omega`, `--cse-global`, `--prefetch-distance`, `--streaming-pattern`, `output_free_sweeps=True`, `--split`
  through `../SweepgenLbmCPU/lbm_split.py`, imported by path, not copied, so the split code is the same).
  - Boundary sweeps: `SparseBoundary(NoSlip(name=...))` and `SparseBoundary(UBB((u_lid,0,0), name=...))`
    with `u_lid` as a symbol. Pull: `NoSlip` and `UBB`. AA: `NoSlipEven/Odd` and `UBBEven/Odd`.
  - Boundary sweeps are generated with `Target.GenericCPU` in **every** family, so their code is
    identical everywhere and only compiler flags differ. Proof: diff of the generated sources.
  - Initial state: rho=1, u=0, generated as plain code.
- **`ldc_boundaries.py`**: `AASparseBoundary(SparseBoundary)` overrides `_get_kernel_assignments` only.
  It uses `BetweenTimestepsIndexing(pdfs, stencil, prev_timestep, "aa", int32, int32)`. The method body is
  otherwise a copy of `sparse.py:215-262`; the pull default is at `sparse.py:222`.
- **`SweepgenLdcCPU.cpp`** (from SweepgenLbmCPU.cpp):
  - Domain: non-periodic, one `cells³` block per process, `getFactors3D(np)`. The block grid is printed.
  - Walls: link predicates on the global wall cell. Lid ⇔ `wallCell.y > yMax`, covering lid edges and
    corners: the effective classic convention, where UniformGridCPU's flags overlap and UBB runs after
    NoSlip (to confirm by reading `lbmpy_walberla/boundary_collection`). NoSlip ⇔ any other cell
    outside the domain. The two link sets are disjoint, so the order does not matter.
  - Pull loop: `init → {StreamCollide → haloExchange → NoSlip → UBB}`. Boundaries never run before step 1,
    because sweepgen's `InitPdfs` leaves slot d of a fluid cell unwritten when d points into a wall.
  - AA loop: `init → {Even → aaPull → BC_Even → Odd → aaPush → BC_Odd}`. The split driver replaces Even/Odd
    exactly as in SweepgenLbmCPU.
  - Result line: `SweepgenLdcCPU variant= compiler= real_t= blocks= cells= steps= output= seconds= mlups=`
    `energy= mass= fieldhash= links_noslip= links_ubb= t_bulk= t_comm= t_bc=`.
    - energy and mass are summed in double and printed with 17 significant digits.
    - `fieldhash` is an XOR over all cells of hash(global cell, bit pattern of rho, u). It does not depend on
      order or decomposition, so it is a bitwise fingerprint of the whole field.
    - Phase timers are extra information; `seconds` is the same single loop timer as presentation3.
  - Asserts: `links_ubb == 5·Nx·Nz` (global).
  - Env `SWEEPGEN_LDC_DUMP=<prefix>` writes the per-rank binary `(x,y,z,rho,ux,uy,uz)` for verification runs only.
  - Env `SWEEPGEN_LDC_OUTPUT=last` works as in presentation3; it is off by default and in the matrix.
- **`README.md`**: variants, walls, loop order, output line, verification.

## Correctness: the verification chain

Each item has a pass criterion; results go into the progress log.

1. **Independent oracle**, `scripts/presentation4/ldc_reference.py`. NumPy, f64.
   - Equilibrium from lbmpy's symbolic method (`create_lb_method(...).get_equilibrium_terms()`, lambdified).
     It does not use pystencils code generation, sweepgen or waLBerla.
   - Pull streaming with explicit ghost cells. Halfway bounce-back NoSlip, and UBB with lbmpy's formula
     `f_in(inv d) = f_out(d) − 6 w_d rho (c_d·u_w)`, where rho is the fluid cell's sum of `f_out` (read from
     lbmpy 2.1.1 `boundaries/boundaryconditions.py:881-905`).
   - The same initial ghost content as InitPdfs, the same step order, and u from the pre-collision PDFs.
   - `compare_fields.py` checks it against app dumps on non-cubic domains: np=1 16³, np=2 (32×16×16),
     np=6 blocks 8³, with 100 and 101 steps.
   - **Pass (f64): max|Δu|, max|Δrho| ≤ 1e-12.** The expected rounding drift is about 1e-13; a real bug shows up at 1e-6 or more.
2. **All variants bit-identical within one compiler, f64.** scalar, autovec and explicit; pull, AA and split;
   with and without CSE and prefetch. Same `fieldhash`, energy and mass. presentation3 had a spread of 0.0 in f64.
3. **Decomposition independence, f64.** 1×64³ and 8×32³ give the same `fieldhash` (the method from notes3).
4. **Invariants.**
   - Mass: `|mass − Nx·Ny·Nz|/(Nx·Ny·Nz) ≤ 1e-12` (f64). This holds because the 5 lid links per cell
     cancel in c_x. It catches missing, doubled or misclassified links.
   - z-mirror symmetry of the dumps (u_z changes sign): ≤ 1e-12 (f64).
   - Link counts equal the oracle's.
   - Subnormal count in the dumped fields is reported (expected 0).
5. **f32.** First calibrate with scalar-f32 against the f64 oracle and record the threshold in the log.
   Every f32 variant must stay within 2× of that error. Mass and energy spread are reported (presentation3: 1.9e-5).
6. **GCC against Clang.** Bitwise equality is not expected (different `-ffp-contract` defaults).
   Pass: both compilers meet the oracle criterion (1) and agree with each other within it.
7. **Mutation tests** (temporary edits on local x86, reverted, then `git diff` is clean). Each must make a check fail:
   - edge links of the lid set to NoSlip,
   - BC_Odd built with prev=EVEN,
   - BC_Odd call dropped,
   - pack info edges.
8. **Existing tests still pass** on x86, 1/2/4 processes: `ctest -R "LbmScenarios|HaloExchange|CommunicationHiding"`
   (24 of 24 in notes3).

## Build audit: -O3, flags, truly scalar

- Configure every tree with `CMAKE_BUILD_TYPE=Release` and `CMAKE_EXPORT_COMPILE_COMMANDS=ON`.
- **Vector trees** (`build-{gcc,clang}-{f32,f64}`): waLBerla defaults, used for autovec and explicit.
- **Scalar trees** (`build-{gcc,clang}-{f32,f64}-scalar`): `WALBERLA_OPTIMIZE_FOR_LOCALHOST=ON` as everywhere
  (same sweepgen target logic, same Clang `-mtune`), plus `-DCMAKE_{C,CXX}_FLAGS_RELEASE="-O3 -DNDEBUG -march=rv64gc"`.
  flags.make puts the release flags after waLBerla's `-march=rv64gcv_zvl256b`, so the last `-march` wins for every
  file, libraries included. Only scalar targets are built there.
- `scripts/presentation4/check_build.py <tree> <scalar|vector> <gcc|clang>` must pass before any timing:
  - Every compile command (libraries and app) has `-O3` as its last `-O`.
  - The last `-march` is the expected one.
  - Clang commands contain `-mtune=spacemit-x60`; GCC commands do not.
  - No `#pragma GCC optimize` or `#pragma clang` in the generated sources.
  - `llvm-objdump` counts RVV instructions:
    - scalar: **0 in the whole executable**; the system libraries are already 0.
    - autovec: v-instructions inside the stream-collide functions, by symbol (reported).
    - explicit: more than 0.
- One extra 1-core run: scalar from the vector tree against scalar from the scalar tree. It shows whether
  presentation3's baseline was affected by RVV in the libraries.
